# ADR 0003: Passwordless-first authentication

## Status
Accepted

## Context
Static DB passwords are a standing secret: they sit in a vault, get
copied into app config, and don't expire unless something remembers to
rotate them. Both clouds now offer identity-based DB authentication
(Entra ID / Managed Identity on Azure, IAM DB auth on AWS) for the
engines this platform targets, which removes the secret entirely for
the common case.

## Decision
Order of preference, strictly in this order, per engine/workload:

1. **Identity auth** — Entra ID auth on Azure PostgreSQL
   Flexible/Azure SQL, IAM DB auth (`rds_iam`) on RDS/Aurora Postgres
   and MySQL, Cosmos DB data-plane RBAC, IAM policies for DynamoDB. No
   secret exists.
2. **Engine-managed secret** — e.g. RDS `manage_master_user_password =
   true`, which hands lifecycle to AWS Secrets Manager's built-in
   rotation. Used only for the bootstrap admin account, never for app
   logins.
3. **Rotation-owned secret** — Terraform creates the login role/user
   *without* a password (or with `ignore_changes = [password]|
   lifecycle.ignore_changes`) plus the secret container and rotation
   schedule. A rotation Lambda/Function owns the actual password value;
   Terraform state never contains it.
4. **Write-only bootstrap** — only for one-time legacy values that
   genuinely cannot use identity auth: `ephemeral "random_password"` +
   a provider/resource `*_wo` / `*_wo_version` argument, bumped to
   rotate. Used as a last resort and must be called out in the
   database request's PR description.

Forbidden outright: non-ephemeral `random_password` for DB credentials,
secrets in `.tfvars`/outputs/CI logs, `sensitive` outputs that expose a
password string to `terraform output`.

RDS/Aurora master-user bootstrap reads the engine-managed secret via an
`ephemeral "aws_secretsmanager_secret_version"` data source scoped to
the L3 stack only, used once to create an IAM-enabled `tf_admin` role,
after which every subsequent apply authenticates as `tf_admin` via IAM
token — the master password is never read again after that first run.

## Consequences
- Engines/clients that cannot do identity auth (legacy JDBC drivers,
  some BI tools) need an explicit, documented exception per
  ADR-tracked workload — this is the expected minority case, not the
  default.
- Rotation functions (Secrets Manager rotation Lambda / Key Vault
  rotation Function) become part of the platform's operational
  surface and need their own IaC and on-call ownership, scoped per
  engine in a later phase.
- `# TODO(verify)`: confirm which write-only arguments the pinned
  `cyrilgdn/postgresql` (~> 1.25) and `azurerm` (~> 4.0) provider
  versions actually expose (`password_wo` support varies by resource
  and provider release) before relying on option 4 for any real
  workload.
